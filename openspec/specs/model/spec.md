# model Specification

## Purpose

The `model` module is the core Eclipse plugin containing the RDBMS metamodel defined in Ecore, EMF-generated Java code, hand-written runtime support (utilities, validation, incremental transformation, CLI integration), and Epsilon scripts for validation and transformation.

## Architecture

The module is organized into three layers:

- **Ecore metamodel** (`model/model/`): Four `.ecore` files define the RDBMS schema structure — `rdbms.ecore` (tables, fields, keys, indexes, operations), `rdbms-datatypes.ecore` (type mappings), `rdbms-namemapping.ecore` (FQN-to-SQL mappings), `rdbms-tablemappingrules.ecore` (relationship rules)
- **Generated code** (`src-gen/`): EMF model interfaces/implementations, builder classes, helper classes, and runtime model support generated by MWE2 workflow
- **Runtime code** (`src/main/java/`): Hand-written classes in `hu.blackbelt.judo.meta.rdbms.runtime` (RdbmsUtils, RdbmsIncremental, RdbmsEpsilonValidator, CheckRdbmsModelCompatibility, RdbmsCloneUtil, RdbmsModelStreamProvider) and `hu.blackbelt.judo.meta.rdbms.cli` (RdbmsValidatorImpl, RdbmsFqnResolverImpl)
- **Epsilon scripts** (`src/main/epsilon/`): EVL validation rules and ETL incremental transformation

Key class hierarchy: `RdbmsModel` contains `RdbmsTable` instances, each with `RdbmsField` subtypes (`RdbmsValueField`, `RdbmsIdentifierField`, `RdbmsForeignKey`). `RdbmsJunctionTable` extends `RdbmsTable` for many-to-many relationships. `RdbmsTableOperation` subtypes track incremental changes.

## Requirements

### Requirement: Model utility querying

RdbmsUtils SHALL provide methods to query tables, fields, foreign keys, and junction tables from an RDBMS model by name.

#### Scenario: Get table by name
- **GIVEN** an RdbmsModel with a table named "Customer"
- **WHEN** `getRdbmsTable("Customer")` is called
- **THEN** an `Optional<RdbmsTable>` containing the matching table is returned

#### Scenario: Get field by table and field name
- **GIVEN** an RdbmsModel with table "Customer" containing field "name"
- **WHEN** `getRdbmsField("Customer", "name")` is called
- **THEN** an `Optional<RdbmsField>` containing the matching field is returned

#### Scenario: Get all foreign keys in a table
- **GIVEN** an RdbmsModel with table "Order" containing foreign keys
- **WHEN** `getRdbmsForeignKeys("Order")` is called
- **THEN** an `Optional<EList<RdbmsForeignKey>>` containing all foreign keys is returned

### Requirement: Table builder initialization

RdbmsUtils SHALL provide static builder methods that create properly initialized tables with identifier fields and primary keys.

#### Scenario: Create new table with builder
- **WHEN** `newRdbmsTableBuilderInit("Customer")` is called
- **THEN** a `RdbmsTableBuilder` is returned with a pre-configured `RdbmsIdentifierField` as primary key

#### Scenario: Create junction table with foreign keys
- **GIVEN** two existing RdbmsTable instances
- **WHEN** `newRdbmsJunctionTableBuilderInit("CustomerOrder", table1, table2)` is called
- **THEN** a `RdbmsJunctionTableBuilder` is returned with two `RdbmsForeignKey` fields referencing the given tables

### Requirement: XMI ID uniqueness validation

RdbmsUtils SHALL validate that all XMI IDs in the model resource are unique.

#### Scenario: Detect duplicate XMI IDs
- **GIVEN** an RdbmsModel where two elements share the same XMI ID
- **WHEN** `validateUniqueXmiids()` is called
- **THEN** an `IllegalStateException` is thrown indicating duplicate IDs

### Requirement: Incremental model transformation

RdbmsIncremental SHALL compute the difference between two RDBMS model versions and produce an incremental model containing create, modify, and delete operations.

#### Scenario: Detect new table
- **GIVEN** a previous model without table "Inventory" and a new model with table "Inventory"
- **WHEN** `transformRdbmsIncrementalModel(previous, new, incremental, dialect, mergeModels)` is called
- **THEN** the incremental model contains an `RdbmsCreateTableOperation` for "Inventory"

#### Scenario: Detect deleted table
- **GIVEN** a previous model with table "Legacy" and a new model without it
- **WHEN** `transformRdbmsIncrementalModel(previous, new, incremental, dialect, mergeModels)` is called
- **THEN** the incremental model contains an `RdbmsDeleteTableOperation` for "Legacy"

#### Scenario: Detect modified field
- **GIVEN** a previous model where table "Customer" has field "name" with size 100, and a new model where size is 200
- **WHEN** `transformRdbmsIncrementalModel(previous, new, incremental, dialect, mergeModels)` is called
- **THEN** the incremental model contains an `RdbmsModifyTableOperation` with an `RdbmsModifyFieldOperation` where `sizeChanged` is true

### Requirement: Model validation via Epsilon EVL

RdbmsEpsilonValidator SHALL execute EVL validation scripts against an RDBMS model and report errors and warnings.

#### Scenario: Validate valid model
- **GIVEN** a well-formed RdbmsModel
- **WHEN** `validateRdbms(log, model, scriptRoot)` is called
- **THEN** no exceptions are thrown

#### Scenario: Validate with expected errors
- **GIVEN** an RdbmsModel with known constraint violations
- **WHEN** `validateRdbms(log, model, scriptRoot, expectedErrors, expectedWarnings)` is called
- **THEN** validation completes, accepting the specified errors and warnings as expected

### Requirement: Model compatibility checking

CheckRdbmsModelCompatibility SHALL compare two RDBMS models and determine if they are structurally identical, providing a detailed change report when they differ.

#### Scenario: Identical models
- **GIVEN** two structurally identical RdbmsModel instances
- **WHEN** `isRdbmsModelIdentical(current, candidate, dialect, reportBuilder, useXmiId)` is called
- **THEN** the method returns `true` and the report builder is empty

#### Scenario: Models with changes
- **GIVEN** two RdbmsModel instances with structural differences
- **WHEN** `isRdbmsModelIdentical(current, candidate, dialect, reportBuilder, useXmiId)` is called
- **THEN** the method returns `false` and the report builder contains details of create/modify/delete operations

### Requirement: CLI model validation integration

RdbmsValidatorImpl SHALL implement the `ModelValidator` interface to bridge the CLI framework with RDBMS model validation.

#### Scenario: Validate via CLI
- **GIVEN** an RdbmsModel instance
- **WHEN** `validate(logger, model)` is called
- **THEN** the model is validated using `RdbmsEpsilonValidator`

#### Scenario: Invalid model type
- **GIVEN** an object that is not an RdbmsModel
- **WHEN** `validate(logger, model)` is called
- **THEN** an appropriate error is raised

### Requirement: FQN resolution

RdbmsFqnResolverImpl SHALL resolve fully qualified names to model elements using a cached lookup strategy.

#### Scenario: Resolve table by FQN
- **GIVEN** a bound FQN resolver with an RdbmsModel containing table "Customer" with fullName "com.example.Customer"
- **WHEN** `resolve("com.example.Customer")` is called
- **THEN** an `Optional<EObject>` containing the matching RdbmsTable is returned

#### Scenario: Resolve field by composite FQN
- **GIVEN** a bound FQN resolver with table "Customer" containing field "name"
- **WHEN** `resolve("Customer#name")` is called
- **THEN** an `Optional<EObject>` containing the matching RdbmsField is returned

#### Scenario: Find by pattern
- **GIVEN** a bound FQN resolver with multiple tables
- **WHEN** `findByPattern(".*Customer.*")` is called
- **THEN** a stream of matching FQN strings is returned

### Requirement: ETL incremental transformation script

The `createIncrementalOperationModel.etl` script SHALL compare PREVIOUS and NEW model contexts and generate incremental operations in the INCREMENTAL context.

#### Scenario: Post-processing cleanup
- **WHEN** the ETL transformation completes
- **THEN** empty modify operations (no field changes and no name changes) are removed from the incremental model

#### Scenario: Operation meta creation
- **WHEN** the ETL transformation runs
- **THEN** an `RdbmsOperationMeta` is created linking previousModel, currentModel, and incrementalModel
